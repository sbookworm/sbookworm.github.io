> 红队测试不只是想办法让模型说出一句违规的话。真正需要测试的是：一段不可信输入，能不能穿过上下文、工具和权限边界，最终变成一次真实动作。

## 先说结论

AI 红队攻击大致经历了三次变化：

1. 早期主要靠手工越狱，让模型暂时偏离安全策略；
2. 随后出现自动化攻击，用一个模型搜索或改写另一个模型的输入；
3. 当模型开始读取网页、邮件、文档、数据库并调用工具后，攻击重点转向间接提示注入、工具链组合和多 Agent 信任边界。

这三类攻击没有互相替代。它们更像是叠加在一起的攻击面：模型可能先被一段外部内容影响，再通过工具调用扩大影响范围，最后由另一个 Agent 接力完成动作。

本文只整理红队视角的攻击图谱，重点是理解攻击面和测试方法，不提供可直接用于现实系统的攻击 payload。所有演练都应放在授权的本地模型、合成数据和隔离环境中进行。

## 红队到底在测什么

如果只把问题定义成"模型有没有说出违规内容"，测试结果很容易失真。一个 Agent 即使没有输出明显有害的文本，也可能已经发生了安全失败：

- 它把外部网页中的一句话当成了系统指令；
- 它读取了不该读取的文件；
- 它调用了参数合法、但组合起来危险的工具；
- 它把低权限 Agent 传来的内容当成了高权限指令；
- 它没有完成危险动作，但已经泄露了内部上下文或凭据线索。

因此，红队测试至少要同时观察四个结果：

| 观察对象 | 要回答的问题 |
| --- | --- |
| 模型输出 | 模型是否偏离任务，生成违规或误导性内容？ |
| 上下文 | 哪段不可信数据影响了模型？它是否被当成指令？ |
| 工具调用 | 模型调用了什么工具，参数是否超出任务需要？ |
| 最终动作 | 是否发生了外发、写入、付款、删除或权限变化？ |

最重要的不是一次成功的"越狱截图"，而是完整的攻击链：输入从哪里来，经过了哪些组件，在哪一步失去控制，造成了什么后果。

## 一、手工越狱：最容易理解的起点

### 1. 角色扮演与虚构包装

最常见的手工越狱会给模型安排一个看似特殊的角色，或者把危险请求包装成小说、剧本、研究报告和虚构对话。例如，攻击者不直接提出请求，而是让模型扮演一个"不受限制的研究员"，再要求它以角色身份完成任务。

这类方法的核心不是某个固定句式，而是利用模型对上下文和角色的敏感性，试图让模型把安全规则解释成故事背景，而不是当前任务的约束。

它的缺点也很明显：

- 对不同模型、不同版本的迁移性有限；
- 很容易被简单的输入和输出审核拦截；
- 攻击者需要不断试错，结果不稳定；
- 即使模型生成了违规文本，也不代表它能进一步调用工具或完成真实动作。

手工越狱仍然值得保留，因为它适合做基线测试。红队可以先用少量、可审计的人工用例，检查模型的基本拒答边界是否正常。

### 2. 多语言和语境切换

模型对不同语言、方言、拼写方式和混合语境的安全表现可能不一致。攻击者可能把请求拆成多种语言，或者使用低资源语言、转写文本和编码后的表达，试图绕过只覆盖主要语言的过滤器。

这里需要注意一个误区：不要把"换一种语言就一定能绕过"当成结论。模型版本、审核层、语言识别器和输出检测器都会改变结果。正确的红队做法是建立多语言测试矩阵，对同一语义在不同表达方式下的结果进行对比。

### 3. Many-shot Jailbreaking

Many-shot 的思路是把大量虚构的"用户—助手"对话放进上下文，让模型从对话惯性中学习一种新的回答模式。它利用的不是一句特别巧妙的话，而是长上下文带来的示范效应。

这类攻击对 Agent 的启发在于：上下文长度本身也是攻击资源。系统即使能够识别短提示中的危险词，也可能没有评估长上下文中大量示例、历史消息和检索结果共同造成的行为变化。

## 二、自动化对抗生成：从写 prompt 变成搜索 prompt

人工写提示词的效率有限。2023 年以后，红队研究越来越多地使用自动化方法，让攻击模型、搜索算法或评估器不断生成候选输入，再根据目标模型的反馈进行优化。

### 1. GCG：白盒对抗后缀

GCG（Greedy Coordinate Gradient）面向可以访问模型参数或梯度信息的研究环境。它尝试找到一段附加在用户输入后的 token 序列，使目标模型更容易生成攻击者指定的结果。

从原理上看，它包含几个步骤：

1. 设定目标输出，并把目标输出的概率作为优化目标；
2. 根据梯度估计，寻找值得修改的 token 位置；
3. 用贪心方式替换候选 token，逐步降低目标损失；
4. 在本地模型上反复搜索，观察生成结果和迁移效果。

GCG 的特点是自动化程度高，生成的后缀可能看起来像乱码。它揭示了一个问题：安全对齐并不等于模型对所有输入扰动都具有鲁棒性。

但 GCG 不应被当成生产环境攻击教程。它通常需要模型访问权限和较高的计算成本，攻击结果也依赖目标模型、模板和解码设置。工程上更有价值的是用它生成测试样本，评估模型和外围防护在输入扰动下的稳定性。

### 2. PAIR：用一个 LLM 攻击另一个 LLM

PAIR（Prompt Automatic Iterative Refinement）把攻击过程变成黑盒迭代：攻击者模型生成候选 prompt，目标模型返回结果后，攻击者模型分析失败原因，再提出下一版候选。

这个过程可以概括为：

```text
攻击模型生成候选输入
        ↓
目标模型返回拒答或回答
        ↓
攻击模型根据结果调整策略
        ↓
继续测试，直到达到停止条件
```

PAIR 不需要读取目标模型的梯度，只需要能够调用目标模型。因此，它更接近商业 API 的现实测试条件。

红队评估 PAIR 时，不能只记录"是否成功"，还要记录查询次数、成本、耗时、不同随机种子的差异，以及目标模型是否在后续对话中恢复正常。否则，单次偶然成功会被误判为稳定漏洞。

### 3. TAP：搜索树加剪枝

TAP（Tree of Attacks with Pruning）可以看作 PAIR 的搜索树版本。它同时探索多条攻击路径，在发给目标模型之前先对候选进行评估，把明显无效或偏离目标的分支剪掉。

它解决的是一个实际问题：黑盒攻击的查询次数有限，不应该把预算浪费在低质量候选上。

从防守角度，TAP 提醒我们不要只用一条固定的拒答样本做评估。更合理的测试应覆盖多条语境变化、多个对话分支和不同的失败反馈，观察攻击者是否能在有限预算内找到行为边界。

### 4. 自动化方法的共同风险

GCG、PAIR 和 TAP 的技术路线不同，但它们有一个共同点：攻击不再依赖某个天才提示词，而是可以被程序批量搜索。

因此，防守方不能只维护一份静态的 jailbreak 黑名单。红队测试应关注：

- 输入经过改写、拆分、翻译后，安全策略是否仍然一致；
- 攻击者能否根据拒答信息逐轮调整；
- 过滤器是否泄露了过多可用于优化的反馈；
- 模型拒答之后，是否仍然执行了工具调用或产生了副作用。

## 三、多模态攻击：安全边界不能只看文本

当模型能够读取图片、音频和视频后，攻击载体就不再局限于聊天框里的文字。

### 1. 图像中的文字

ArtPrompt、FigStep 等方法把指令放进 ASCII art、排版图像或视觉设计中。系统可能先经过图像编码器和 OCR，再把识别出的内容交给语言模型。如果文本安全过滤只检查用户直接输入的文字，就可能漏掉视觉路径中的指令。

这类攻击的重点不在于某一种字体或图片样式，而在于跨模态处理链：

```text
图像输入 → OCR/视觉编码 → 文本或视觉 token → 语言模型 → 输出/工具调用
```

每一个箭头都可能重新解释内容，也可能绕开上一层已经做过的检查。

### 2. 音频和视频

音频可以携带用户不容易注意到的语音内容，视频则可以通过多帧拼接和上下文变化影响模型判断。红队测试不能只拿一张静态图片做一次检查，还应测试：

- OCR 结果与原图内容是否一致；
- 音频转写前后是否丢失安全标签；
- 单帧看似正常的内容，组合后是否形成新指令；
- 多模态内容是否能影响后续工具调用。

安全检查应尽量靠近每个模态转换节点，而不是只在最终文本输出处做一次审核。

## 四、间接提示注入：2024 年以后更现实的主战场

直接提示注入是攻击者在聊天框里输入恶意指令。间接提示注入则把指令藏进第三方数据，等待 Agent 自己读取。

### 1. 典型攻击链

```text
攻击者污染网页、邮件、PDF、数据库字段或协作工具消息
                         ↓
用户让 Agent 查询、总结或处理这些内容
                         ↓
Agent 调用检索、浏览器、邮件或文件工具
                         ↓
恶意内容进入上下文窗口
                         ↓
模型把数据中的文字误当成当前任务指令
                         ↓
生成误导性输出，或继续调用高风险工具
```

这类攻击比直接越狱更难处理，因为用户本人可能没有输入任何恶意内容。用户只是提出了一个正常请求，例如"总结这封邮件"或"看一下最近的交易"。

### 2. 为什么数据和指令很难分开

在传统程序中，代码和字符串通常有明确的语法边界。对 LLM 来说，系统消息、用户问题、检索结果和工具返回内容最后都会变成 token 序列。

给数据加上"以下内容仅供参考"的标签有帮助，但这仍然是模型层面的提示，不能被当成唯一防线。真正的边界应该落在应用层：

- 工具返回内容默认标记为不可信数据；
- 数据不能改变系统配置、权限和工具白名单；
- 模型只能通过结构化接口请求动作；
- 高风险动作由独立组件校验和审批。

### 3. 为什么金融和企业场景更危险

金融交易备注、邮件正文、CRM 备注、客服记录和工单评论，原本都只是普通业务字段。一旦 Agent 开始读取它们，这些字段就可能变成指令投递渠道。

Blue41 对 Bunq AI 助手的案例正好说明了这一点：攻击者通过一笔极小金额的转账，把内容写进交易备注；用户随后查询交易，备注进入模型上下文，助手最终生成了伪装成银行通知的钓鱼信息。

这个案例的关键不在于金额，而在于攻击者利用了一个正常业务流程，把外部可控文本送进了一个受信任的界面。

## 五、Agent 工具链：单步合理，组合危险

Agent 攻击的风险经常不在某一个工具，而在多个工具的组合。

例如，下面每一步单独看都可能是合理操作：

```text
读取联系人列表
    ↓
整理联系人信息
    ↓
生成邮件草稿
    ↓
发送邮件
```

但如果第一步读取了不该访问的数据，或者最后一步没有人工确认，这条链就可能变成数据外发。

红队测试需要模拟这类组合，而不是逐个工具做孤立检查。重点包括：

- 读工具的结果能否直接成为写工具的参数；
- 一个工具返回的内容能否改变下一步工具选择；
- 低风险工具是否能被串成高风险路径；
- Agent 是否会在失败后无限重试；
- 工具参数是否只校验了类型，没有校验业务语义；
- Agent 是否能绕过审批，直接调用外发、付款或删除类操作。

因此，工具白名单只是起点。实际防护还需要工具名、参数 schema、调用顺序和滑动窗口一起审计。

## 六、多步攻击和资源耗尽

攻击者不一定要让模型立刻做一件明显危险的事，也可以诱导 Agent 进入持续循环：

- 反复搜索相似内容，消耗 token 和 API 预算；
- 不断调用失败工具，形成调用风暴；
- 让 Agent 在多个子任务之间来回跳转；
- 诱导它生成过长输出或读取过大的文件；
- 让它不断尝试权限更高的工具。

这些攻击的结果可能是拒绝服务、成本失控，或者让正常请求排队等待。红队报告不能只写"模型没有被越狱"，还要写清楚在预算、时间和步骤上是否出现异常。

## 七、多 Agent 协同攻击：信任会沿着消息传播

多 Agent 系统把任务拆给多个角色：规划 Agent、检索 Agent、执行 Agent、审核 Agent。这样做能提高效率，但也增加了信任传播路径。

一个典型风险是：

```text
低权限 Agent 读取了被污染的外部内容
          ↓
它把内容整理后传给高权限 Agent
          ↓
高权限 Agent 把上游消息当成可信结论
          ↓
高权限 Agent 执行了外部动作
```

这里的问题不是单个 Agent 是否遵守了 system prompt，而是 Agent 之间是否有可验证的消息来源、权限和意图标签。

红队应重点测试：

- Agent A 能否伪造 Agent B 的身份或消息格式；
- 上游 Agent 的输出是否会自动获得更高信任等级；
- 高权限 Agent 是否验证了任务来源和动作范围；
- 一个 Agent 被注入后，污染能传播多远；
- 是否存在低权限到高权限的隐式升级路径。

多 Agent 协作不能只靠"大家都遵守协议"。协议必须有应用层校验，权限也必须绑定到具体动作，而不是绑定到一段自然语言描述。

## 八、攻击演进时间线

```text
2022-2023     手工越狱：DAN、角色扮演、虚构包装
     ↓
2023-2024     自动化对抗：GCG、PAIR
     ↓
2024          搜索优化：TAP、Many-shot 等
     ↓
2024-2025     跨模态攻击：ArtPrompt、FigStep、OCR 注入
     ↓
2024-2026     间接注入：网页、邮件、PDF、数据库和协作工具
     ↓
2025-2026     Agent 攻击：工具链、多步调用、资源耗尽、多 Agent 信任传播
```

这条时间线不是说旧攻击已经失效。更准确的理解是：模型能力越强，外部数据源越多，攻击者越有机会从"影响回答"升级到"影响系统动作"。

## 九、红队应该怎样设计一次测试

### 第一步：先写威胁模型

测试前先回答：

- 资产是什么？用户数据、凭据、资金、代码还是系统配置？
- 攻击者能控制哪些输入？聊天、网页、邮件、文件、交易备注还是插件返回值？
- Agent 有哪些工具？哪些工具会产生不可逆副作用？
- 哪些动作必须人工确认？
- 失败时的最大损害是什么？

没有威胁模型，红队很容易陷入"多找几个 jailbreak prompt"，却没有测试真正的业务风险。

### 第二步：使用合成数据和隔离环境

测试环境至少应满足：

- 使用虚构用户、虚构账户和虚构凭据；
- 工具调用指向本地 mock 服务；
- 外发、付款、删除等动作默认进入模拟队列；
- 记录每一轮输入、上下文、工具调用和最终状态；
- 设置最大步骤数、最大 token 数和最大工具调用次数。

红队的目标是验证控制边界，不是把真实系统当作实验场。

### 第三步：建立攻击矩阵

可以用下面的维度组织用例：

| 维度 | 示例 |
| --- | --- |
| 入口 | 聊天框、网页、邮件、PDF、数据库字段、工具返回值 |
| 载体 | 纯文本、长上下文、图片、音频、跨 Agent 消息 |
| 目标 | 改变回答、泄露上下文、调用工具、外发数据、修改状态 |
| 方式 | 手工越狱、自动改写、间接注入、多步组合、权限传播 |
| 约束 | 查询预算、时间窗口、工具权限、人工审批、最大步骤数 |

测试矩阵的价值在于让结果可比较。每次模型升级、提示模板变更或工具增加后，都可以重跑同一组用例。

### 第四步：用动作结果而不是文本结果判定

对普通聊天模型，输出是否违规可能是主要指标。对 Agent，至少还要记录：

- 高风险工具调用成功率；
- 不可信内容影响工具选择的比例；
- 参数越权或业务语义越权次数；
- 从注入发生到检测的延迟；
- 从检测到阻断的延迟；
- 在被阻断后是否仍能通过其他路径完成动作；
- 单次攻击消耗的 token、时间和工具预算。

红队报告最终要落到业务后果，而不是停留在"模型回答有点奇怪"。

## 十、从红队结果反推防御优先级

红队攻击图谱最终要服务于工程决策。我的判断是，防护优先级可以按下面的顺序落地：

1. **先收敛输入面**：不必要的网页、邮件、备注和历史记录不要送进模型；
2. **再隔离不可信数据**：工具返回内容不能直接改变指令、权限和工具配置；
3. **约束工具和参数**：使用结构化 schema、参数白名单和业务规则校验；
4. **高风险动作人工确认**：付款、外发、删除、改权限等操作不能只由模型决定；
5. **独立做检测和 containment**：检测组件失效时，阻断组件仍应能工作；
6. **设置预算熔断**：限制步骤、token、工具调用和运行时间；
7. **记录完整轨迹**：事后能够复原攻击输入、上下文来源和动作链。

这里最重要的一条仍然是：关键防护逻辑放在模型之外。system prompt 可以作为提示，但不能成为权限系统、审批系统和审计系统的替代品。

## 最后总结

AI 红队攻击已经从"让模型说错一句话"发展到"让系统在正常业务流程里做错一件事"。

手工越狱测试模型的拒答边界；GCG、PAIR、TAP 测试模型在自动化搜索下的稳定性；多模态攻击测试视觉、音频和文本之间的安全断层；间接提示注入测试外部数据是否会变成指令；工具链和多 Agent 攻击则进一步测试权限、信任和动作边界。

对 Agent 来说，真正需要问的不是"模型有没有被说服"，而是：

> 攻击者控制的一段内容，能不能通过系统中的某条路径，最终影响一个不该发生的动作？

如果答案是"能"，那么这就是红队需要提交的核心发现。模型是否承认自己被注入，只是次要信息。
